# Companies: manual test guide

A full walkthrough of the companies feature with real accounts and real email, from creating a company in Thakhin to every flow around it. Work through the parts in order, because later parts reuse the people and cards from earlier ones.

Button and field labels come from the code. If one doesn't match the UI, update this guide.

This guide is also the source for the end-to-end tests. Keep step numbers stable, and write every outcome as an **Expected** line that a test can assert. [Notes for e2e tests](#notes-for-e2e-tests) at the end covers what changes when a test runs a step instead of a person.

## 0. Setup

**Accounts.** Gmail aliases all land in one inbox but count as separate La Persona users.

| Who    | Email                      | Role in these tests                       |
| ------ | -------------------------- | ----------------------------------------- |
| **T**  | your Thakhin admin account | platform admin                            |
| **A**  | `you+admin@gmail.com`      | company admin                             |
| **M1** | `you+m1@gmail.com`         | member, offboarded later                  |
| **M2** | `you+m2@gmail.com`         | new holder after reassignment             |
| **M3** | `you+m3@gmail.com`         | invited and then cancelled                |
| **V**  | `you+visitor@gmail.com`    | La Persona user who exchanges contacts    |
| **P**  | `you+personal@gmail.com`   | owner of a personal card, for pause tests |

Replace `you` with your Gmail name, for example `yanaunghein311+admin@gmail.com`. La Persona stores the full address with the `+` part, so each alias is a different account.

**Before you start:**

- Run `bun run db:migrate`. Migrations up to `0026` must be applied.
- Make sure the dev mailer actually sends email.
- Run `bun run dev`.
- Sign in once as **V** and create a personal card. Seamless exchange (5.5.2, 5.7.6) needs the visitor to have a card.

**Signing in.** La Persona has no passwords. Every account signs in with a magic link.

1. Go to `/sign-in` and enter the alias email.
2. Open the "Your LA PERSONA magic sign-in link" email. Check its **To** line: Gmail may group the links for several aliases into one thread.
3. Copy the link into the window for that person. The link signs in whichever browser window opens it.
4. The first link for an address creates the account. Links expire after 30 minutes.

Don't use Google, GitHub or LinkedIn sign-in for the alias accounts. Those use your real email without the `+` part, so invites to the alias won't match.

**Windows:**

- One normal window for **T**, later also used for **A**.
- One private window per other person. Sign out between people, or use separate browser profiles.
- Check public `/c/...` pages in a signed-out private window unless a step says otherwise.

**Time-based states.** "Expired" can't be reached quickly through the UI. Steps marked ⚠️ edit the database with `bun run db:studio`.

// Department in another company: expect 404, and Beta's department unchanged

Renaming doesn't change the slug, so Acme stays `acme-test-co` unless you edited the slug in Thakhin.

**Thakhin API check:** creating a company with `ownerEmail` in the request body should return 400.

**Payment API check:** `POST /api/admin/organizations/{organizationId}/payments` with both `termYears` and `endAt`, or with neither, should return 400. Creating cards with an `endAt` field ignores it.

### 5.13.7 Image uploads

## Part 5.14: Reliability (API)

What happens when people retry, double-submit, work in two tabs, or email is down. Real users do all of these. Each case says what must stay true.

"At once" means the requests overlap: send them together with `Promise.all`, as separate signed-in contexts where the case needs two people. No case may return a `500`, and the [invariants](#invariants) must hold after every one.

### 5.14.1 Accept in two tabs at once

1. **M1** has a pending invite. As **M1**, send `PATCH /api/invitations/<id> { status: 'accepted' }` twice at once.
2. Expected:
   - At least one call returns `200`. The other returns `200` (it finished second and sees **M1** already holds the card), `409` "This invitation was just accepted. Reload the page.", or `400`.
   - **M1** has exactly one membership in Acme, holds the card, and can open it.
   - The invite is `accepted`.
3. The same holds for a community invite: one membership and one community card.

### 5.14.2 Accept after the invite was cancelled

1. **A** cancels **M3**'s invite while **M3** has the invite page open. **M3** then clicks **Accept Invitation**.
2. Expected: "This invitation has expired or was already processed.", **M3** has no membership in Acme, and the card stays **Vacant**.

### 5.14.3 Expired invite, then resend

1. Set the invite's `expires_at` to yesterday (fixture). **M3** accepts.
2. Expected: "expired or already processed", and nothing changes.
3. **A** clicks **Resend invite**. Expected: a new email arrives and the same link now accepts.

### 5.14.4 Create the same batch twice at once

1. As **T**, send the same `POST /api/admin/organizations/<id>/company-cards` twice at once (a network retry).
2. Expected: one `201`; the other `409` with code `company_invite_exists`. Each email has one card, one pending invite and one payment.
3. Retry the same body after the first finished. Expected: `409` "…already has a pending invite to another card", and nothing new is created.

### 5.14.5 Assign the same vacant card twice at once

1. As **A**, send `POST /api/cards/<vacant-slug>/invitations` twice at once, for two different emails.
2. Expected: one `200`, the other `409` "This card was just changed. Reload and try again." If the first finished before the second started, the second is an ordinary reassignment and also returns `200`.
3. Either way, the card has exactly one pending invite, and its old link is retired only once.

### 5.14.6 Assign two vacant cards to the same person at once

1. As **A**, assign two different vacant cards to **M3**'s email at once.
2. Expected: one `200`, the other `409` with code `company_invite_exists`. **M3** has one pending invite, and the other card stays **Vacant**.

### 5.14.7 Record the same payment twice

1. As **T**, open **Record a payment** for Alice and Nina, and send that request twice at once.

### Invariants

After every company test, check that test's company in the database. A failure here means data is broken even when the page looked fine.

1. A card has at most one open holder (`card_assignment.ended_at` is null), and `card.user_id` is that holder.
2. Every held card's holder is a member of the company, and every member holds exactly one card there.
3. A card has at most one pending invite, a held card has none, and a person has at most one pending invite in the company.
4. Every card has exactly one `card_subscription` row.
5. Once anyone has accepted an Admin invite, the company has at least one admin.
6. A retired slug never belongs to a live card (`retired_card_slug.slug` isn't any `card.slug`).

The database now enforces one membership per person and one pending card invite per email (migration `0027`), so checks 2 and 3 should never fail on those. They still guard the rest.

## Notes for e2e tests

**Naming.** Name each test after its step, for example `5.3.1 admin accepts the invite`, so a failure points back to this guide. When a flow changes, update the guide and the test together.

**Independent tests.** Here the parts run in order and share state. A test should build what its part needs with fixtures instead of running every earlier part:

| Part | Needs before it starts                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------------------------- |
| 1    | a platform admin (**T**)                                                                                              |
| 2    | a company with company settings                                                                                       |
| 3    | pending card invites for **A** (Admin) and **M1** (Member); **M1** and **V** with personal cards                      |
| 4    | an active admin card, an active member card, and a pending invite                                                     |
| 5    | an active member card; **V** with a personal card                                                                     |
| 6    | an active member card with contacts collected on it; for 5.6.6, two active admins                                     |
| 7    | a vacant card that had a holder                                                                                       |
| 8    | a card with a pending invite that nobody has accepted                                                                 |
| 9    | two active company cards                                                                                              |
| 10   | a company card and a personal card, each with `current_period_end_at` in the past; one community card                 |
| 11   | a company with one admin, and a member holding a company card                                                         |
| 12   | two companies, each with a department                                                                                 |
| 13   | two companies; in Acme an active member, a vacant card, and a card reassigned with contacts from both holders         |
| 14   | a company with an active admin, a pending invite and a vacant card that had a holder; Mailpit chaos for 5.14.8–5.14.9 |

**Accounts.** Generate a fresh address per run and person (for example `e2e+<run-id>-admin@…`), so reruns don't collide with earlier accounts and invites.

**Signing in.** A test shouldn't wait on a real inbox. Either read the magic link from a captured email (a stubbed mailer or a test inbox), or create the session directly in a fixture.

**Invite links.** Take the link from the captured invite email. The invitation id is the last path segment of `/invite/community/accept/<id>`.

**Email assertions.** Where a step expects an email, assert the recipient and the subject through the captured mail. For example, 5.2.1 expects an admin invite to **A**, and 5.4.4's resend expects a second email to **M3**.

**Time-based steps (⚠️).** Set `card_subscription.current_period_end_at` in a fixture instead of editing it in db:studio. The app computes expiry from that date, so a test doesn't need to wait for the `subscriptions:expire` task.

**Copy.** Toast text and the paused or retired page copy are quoted in **Expected** lines, so a copy change should update this guide and the test together.

**Reliability cases (Part 5.14).**

- Overlapping requests use `Promise.all` on one request context per person. Don't add sleeps.
- Email outages use Mailpit's chaos mode. `tests/docker-compose.yml` starts Mailpit with `MP_ENABLE_CHAOS=true`. Checked on v5.1.27: with `{"Sender":{"ErrorCode":451,"Probability":100}}`, sends fail at once with `451`, and the mailer doesn't retry.
  - Turn it on with `PUT http://localhost:8025/api/v1/chaos` and that body.
  - Reset it in `finally` with `Probability` `0`, so one failing test can't break the rest.
- The [invariants](#invariants) are one SQL check run in `afterEach` for the company the test created.

**API checks.** Part 5.12 and the `ownerEmail` check have no UI, so they become API-level tests. Expect 404 for the other company's department and for company card requests, and 400 for creating a company with an owner.
