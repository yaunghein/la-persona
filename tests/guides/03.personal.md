# Personal workspace and cards: manual test guide

A person's own workspace: their personal cards, card requests, renewals and upgrades, the public card page, and the contacts it collects. Company and community cards live in other guides; this one checks only how they sit next to personal cards.

Button and field labels come from the code. If one doesn't match the UI, update this guide.

This guide is the source for `tests/03.personal.test.ts`. Keep step numbers stable, and write every outcome as an **Expected** line that a test can assert. [Decisions](#decisions) at the end records the gaps found while writing it and how each was settled.

## 0. Setup

| Who   | Email                     | Role in these tests                       |
| ----- | ------------------------- | ----------------------------------------- |
| **T** | your Thakhin admin        | platform admin, reviews requests/payments |
| **A** | `you+alice@gmail.com`     | owner of the personal cards under test    |
| **B** | `you+bob@gmail.com`       | another user with a personal card         |
| **V** | signed-out private window | anonymous visitor                         |

**Before you start:** `bun run db:migrate`, active **Standard** and **Premium** plans in `subscription_plan`, real dev email, `bun run dev`.

**Time-based states (⚠️)** edit `card_subscription.current_period_end_at` with `bun run db:studio` (a fixture in e2e).

## Part 1: The personal workspace

### 1.1 Created on first sign-in (A)

1. **A** signs in for the first time.
2. Expected: one organization of type `personal`, named "<name>'s Space", slug `<name>-space-<id>`, with **A** as its only member (`admin`). The session's active workspace is it.

### 1.2 Only one, ever (A)

1. Sign out and in again; also sign in from a second browser.
2. Expected: still exactly one personal workspace.
3. **T** tries `POST /api/admin/organizations` type **Personal** with **A**'s user id. Expected: `409` "User already has a personal organization."

### 1.3 Private to its owner (B)

1. **B** opens `/platform/<a-personal-slug>` and `/platform/<a-personal-slug>/cards`.
2. Expected: never **A**'s data. The API calls behind them (`GET /api/organizations/<a-personal-slug>`, `…/cards`) return `404`.

### 1.4 No members, no invites

1. As **A**: `POST /api/organizations/<a-personal-slug>/invitations` → `403` "This is only available for community organizations.", no email.
2. `GET /api/organizations/<a-personal-slug>/join-link` → the same `403`.

## Part 2: Requesting a card

### 2.1 New design (A)

1. **Cards** → **Request New Card** → **New Design**. Fill Full Name, title, phone, email, website, two links. Upload a receipt with **Upload Payment Receipt**, then **Send Request**.
2. Expected:
   - `201` with `requestId`, `paymentId`, `cardSlug`, `planCode: 'premium'`.
   - **A** gets a submission email; every `ADMIN_EMAILS` address gets the team email with a link to `/thakhin/requests`.
   - The card appears in **A**'s Cards as pending approval. Its subscription is `pending_approval`, its payment `submitted` with the premium price × 1 year from the server's price table.

### 2.2 Existing design (A)

1. **Request New Card** → **Existing Design**, choose one of **A**'s cards.
2. Expected: the new card copies the source's Spline, wallpaper and card back. Plan follows the source: `standard` if the source is standard or on trial, `premium` if premium, `premium` for `founder-club`.

### 2.3 Prices come from the server

1. Send the request with an extra `amountMinor: 1`, `planCode: 'standard'` and `userId: <B's id>` in the body.
2. Expected: `201`, the extra fields are ignored. Price and plan are the server's; the card belongs to **A**.

### 2.4 Design source must be yours

1. `existing_design` with `sourceCardId` = one of **B**'s cards.
2. Expected: `400` "Selected card design is invalid." Nothing is created.

### 2.5 Receipt must be our upload

| `receiptUrl`                 | Expected                                   |
| ---------------------------- | ------------------------------------------ |
| missing or empty             | `400` "Please upload a payment receipt."   |
| `https://evil.example/r.png` | `400` "Upload the image again."            |
| `javascript:alert(1)`        | `400`                                      |
| a bucket URL from our bucket | `201`, stored as a key (`organizations/…`) |

### 2.6 Thakhin approves (T)

1. `/thakhin/requests` → approve **A**'s request.
2. Expected: the request is `approved`, its payment `approved`, the subscription `active` for 1 year from approval, and **A** gets an approval email.

### 2.7 Thakhin declines (T)

1. Decline a second request.
2. Expected: request `declined`, payment `rejected`. The card's subscription leaves `pending_approval` and becomes `expired`, so its public page shows "Card paused".
3. Approving it afterwards returns `409` "Only pending requests can be approved."

### 2.8 Approve without a receipt

1. A request with no receipt (legacy data, fixture). Approve. Expected: `409` "Cannot approve a request without a payment receipt."

### 2.9 A new card is live while it waits for approval

1. Open the pending card from 2.1 at `/c/<slug>` signed out, before **T** reviews.
2. Expected: the card shows normally. A brand-new card has no paid period yet, so waiting for approval doesn't pause it (decided, [D6](#decisions)).
3. After **T** declines it (2.7), the same link shows "Card paused".

## Part 3: Editing a card (A)

### 3.1 Save contact info

1. Edit Name, title, company, phone with country code, email, website, then save.
2. Expected: "Info saved successfully." and the public page shows the changes after reload.

### 3.2 Links

1. Add links of each type, reorder by dragging, remove one, save.
2. Expected: order is kept. Up to 30 links; a 31st returns `400`.

### 3.3 Link and website validation

| Field       | Value                                     | Expected              |
| ----------- | ----------------------------------------- | --------------------- |
| social link | `javascript:alert(1)`                     | `400`                 |
| social link | `data:text/html,<script>…`                | `400`                 |
| social link | `mailto:a@b.co`, `tel:+959…`, `https://…` | saved                 |
| website     | `ftp://x`, `mailto:a@b.co`                | `400`                 |
| website     | empty string                              | saved as empty (null) |
| email       | `not-an-email`                            | `400`                 |

The `400` names the field in `details` and never echoes the value.

### 3.4 Photo

1. **Upload Photo** with PNG, JPEG and WebP. Expected: each saves as a key `organizations/<a-space-id>/<uuid>.<ext>`.
2. SVG, GIF, or a file over 5 MB. Expected: refused before upload (`400` from `POST /api/organizations/<slug>/uploads`).
3. `PATCH /api/cards/<slug> { avatarUrl: 'https://evil.example/a.png' }` → `400`.

### 3.5 Fields the owner can't set

1. `PATCH /api/cards/<slug>` with `userId`, `organizationId`, `splineUrl`, `wallpaperUrl`, `cardBackUrl`, `departmentId`.
2. Expected: `200`, and none of those changed (they're not in the contract, or ignored for personal cards).

### 3.6 Change the card URL

1. Set slug to `alice-test`. Expected: saved; `/c/alice-test` works; the old `/c/<old-slug>` returns "Page not found".

### 3.7 Slug rules

| Slug               | Expected                                                                |
| ------------------ | ----------------------------------------------------------------------- |
| `Alice Test`       | `400` (spaces)                                                          |
| `ALICE`            | saved as `alice`                                                        |
| `-alice`, `alice-` | `400`                                                                   |
| 81 characters      | `400`                                                                   |
| **B**'s slug       | `409` "That card URL is already taken. Please choose a different slug." |

### 3.8 Visibility

1. Set **Members only** (`visibility: 'members'`).
2. Expected: signed out, `/c/<slug>` asks to sign in (`GET /api/public/cards/<slug>` → `401` "Sign in to view this card."). Signed in as **B**, it shows.
3. Set back to public. Expected: signed-out visitors see it again.

### 3.9 Phone normalization

1. Save phone `09 123 456 789` with country Myanmar, then `+959123456789` with no country.
2. Expected: the phone is stored as typed, and in both cases the public card's call link is `tel:+959123456789`.

## Part 4: Deleting a card (A)

### 4.1 Delete own personal card

1. Card ⋯ → **Delete card**. The dialog says the card and its link stop working, a payment waiting for review is withdrawn, and the contacts collected on it stay in Contacts. Click **Delete**.
2. Expected: "Card deleted" — "Its contacts stay in your Contacts.", `204`.
3. Expected: the card is gone from **A**'s Cards and `/c/<slug>` returns "Page not found". `GET`/`PATCH`/`DELETE /api/cards/<slug>` return `404`.
4. Expected: the row stays in the database with `removed_at` set and `user_id` still **A**. The slug stays reserved: setting another card's slug to it returns `409`.
5. Expected: payments for that card remain in `/thakhin/payments` and in **A**'s billing history.

### 4.2 Contacts stay after delete

1. **B** exchanges contacts with **A**'s card (6.3), then **A** deletes that card.
2. Expected: **A**'s Contacts still lists **B**, tagged with the deleted card. **A** can still label, note and delete that contact (`PATCH`/`DELETE /api/contacts/<id>` → `200`/`204`).
3. Expected: on **B**'s side, the contact for **A** now shows the details captured at exchange time, with no link to **A**'s dead card.
4. Expected: CSV export includes it.

### 4.2a Delete a card with a receipt waiting for review

1. Submit a renewal on a card (5.2), then delete the card before **T** reviews it.
2. Expected: the payment becomes `rejected` with the note "Card removed by its holder", any linked pending card request is withdrawn, and `/thakhin/payments` no longer offers to approve it.

### 4.3 Community and company cards can't be deleted here

1. `DELETE /api/cards/<a's community card>` and `<a's company card>`.
2. Expected: `403`, nothing changes. An Organizer deleting their own community card sees "Community cards are removed when you leave the community."; a company member gets the generic `403`.

### 4.4 Someone else's card

1. As **B**, `DELETE /api/cards/<a-slug>` → `404`. **A**'s card is unchanged.

## Part 5: Renewal and premium upgrade

### 5.1 Quote (A)

1. `GET /api/cards/<slug>/payment-quote?kind=renewal` and `?kind=premium_upgrade`.
2. Expected: amounts and plan from the server's price table; no client input changes them.
3. On a community or company card: `403` "Community cards are covered by the community."

### 5.2 Submit a renewal (A)

1. On an active standard card, open the renewal slideover, upload a receipt, **Confirm Payment**.
2. Expected: `201` `{ status: 'submitted' }`. One `submitted` payment with one item for this card, priced by the quote. **A** and the team get submission emails. The period isn't extended yet.

### 5.3 Thakhin approves (T)

1. `/thakhin/payments` → approve.
2. Expected: payment `approved`; the subscription is `active` and its end moves forward by the paid term from the current end (or from today if already ended). **A** gets "approved".

### 5.4 Thakhin rejects (T)

1. Submit another renewal; **T** rejects with a reason.
2. Expected: payment `rejected` with the reason in its note; the period is unchanged; **A**'s email includes the reason.

### 5.5 Premium upgrade (A)

1. **Get Our Premium Card** → upload receipt → submit.
2. Expected: a `submitted` payment linked to a new `existing_design` card request. `/thakhin/payments` refuses to decide it directly: `409` "This payment is linked to a card request. Decide it from the Requests page." Approving the request approves the payment and switches the plan to premium.

### 5.6 Expired card, owner's view ⚠️

1. Set `current_period_end_at` to yesterday.
2. Signed out: "Card paused — This card is taking a short break. Please check back soon." No button.
3. Signed in as **A**: "Your card is paused — …" with **Extend my card**, which opens the renewal slideover (`?payment=renewal`). Closing it removes the query.
4. Signed in as **B**: the signed-out text, no button.

### 5.7 A receipt doesn't unpause an expired card

1. ⚠️ Expire **A**'s card (5.6). Submit a renewal with a receipt.
2. Expected: `201`, and the card **stays paused** (signed out: "Card paused"; exchange `409`) until **T** approves.
3. **T** approves. Expected: the card is live again; its period is the one the payment item was priced for at submission.
4. **T** rejects instead. Expected: still paused; **A** can submit again.

### 5.7a An active card stays live during review

1. On an **active** card, submit a renewal.
2. Expected: the card stays live while the payment waits, until its current period ends.

### 5.8 One payment waiting at a time

1. Submit a renewal, then submit another (or an upgrade) for the same card before **T** decides.
2. Expected: the second returns `409` "A payment for this card is already waiting for review." and the slideover shows that message. One `submitted` payment exists.
3. Send two `POST /api/cards/<slug>/payments` at once. Expected: one `201`, one `409`.
4. After **T** decides the first, a new submission works.

### 5.9 Legacy cards

1. A personal card with no `card_subscription` row (pre-subscription data, fixture).
2. Expected: the card stays live (no pause), and renewal quotes treat it as expired.

## Part 6: The public card and contacts

### 6.1 View and link clicks (V)

1. Open `/c/<slug>`, click a link, save the contact (vCard).
2. Expected: **A**'s analytics count one view, one link click, one save. Reloading in the same browser within 10 minutes doesn't add a view (a cookie remembers the visitor).

### 6.2 Exchange contact by form (V)

1. **Exchange Contact**, enter name and email. Expected: "You're all set!", **A** gets a notification email, the visitor gets "{A's name}'s contact details" with a **VIEW PERSONA CARD** link to `/c/{slug}`, and the contact appears in **A**'s Contacts.
2. Script-like input in the name (`<img src=x onerror=alert(1)>`). Expected: shown as text in Contacts, the email and the CSV; nothing executes. A CSV cell starting with `=`, `+`, `-` or `@` is escaped so spreadsheets don't run it.

### 6.3 Seamless exchange (B)

1. **B**, signed in with a card, exchanges on **A**'s card.
2. Expected: "Successfully Connected". **A** sees **B** in Contacts and **B** sees **A**. Doing it again doesn't create a second contact on either side.
3. `POST …/contact-exchanges { mode: 'seamless', cardId: <someone else's card> }` as **B** → `404` "Card"; **B** can only exchange with a card they hold.

### 6.4 Exchanging with yourself

1. **A** exchanges seamlessly on their own card. Expected: `400` "You cannot exchange contact with your own card." No contact is created.

### 6.5 Paused cards take nothing ⚠️

1. With the card expired: exchange returns `409` "This card is currently unavailable.", and views and clicks aren't recorded.

### 6.6 Rate limits

Checked by hand, not in e2e (see [Not covered by e2e](#not-covered-by-e2e)): the e2e server runs with rate limits off, because every request comes from one IP.

### 6.7 Contacts are private (B)

1. Take one of **A**'s contact ids. As **B**: `PATCH /api/contacts/<id>` and `DELETE /api/contacts/<id>` → `404`; nothing changes.
2. **A**'s contact labels: as **B**, `PATCH /api/contact-labels/<a-label-id>` → `404`.

### 6.8 Contacts list and export (A)

1. **Contacts** shows contacts from all of **A**'s cards — personal, community and company — each tagged with its card.
2. Export CSV. Expected: only **A**'s contacts: from cards **A** holds, plus cards **A** deleted (4.2) or held in a community **A** left (`04.communities.md` 2.3, 2.5). Never contacts of a company card **A** was offboarded from.

## Part 7: Access checks (API)

As **B** on **A**'s things, every call returns `404` and changes nothing:

- `GET`, `PATCH`, `DELETE /api/cards/<a-slug>`
- `GET /api/cards/<a-slug>/subscription`, `/payment-quote`, `/holders`
- `POST /api/cards/<a-slug>/payments`
- `POST /api/organizations/<a-personal-slug>/card-requests`
- `POST /api/organizations/<a-personal-slug>/uploads`

Signed out, the same calls return `401`.

## Part 8: Reliability (API)

### 8.1 Two tabs edit the same card

1. Open the editor in two tabs. Save a phone change in tab 1, then save a link change in tab 2 without reloading.
2. Expected: both `200`. The last save wins: tab 2's form also carries the old phone, so tab 1's phone change is overwritten. This is the known behaviour (no edit conflict detection).

### 8.2 Two cards take the same slug at once

1. **A** and **B** both set slug `same-slug` at once.
2. Expected: one `200`, one `409` "That card URL is already taken. Please choose a different slug." Never `500`.

### 8.3 Approve and reject the same payment at once (T)

1. Two Thakhin tabs approve and reject one payment at once.
2. Expected: one succeeds, the other `409` "This payment was already processed." The subscription matches the winner.

### 8.4 Request submitted while email is down

1. Mailpit chaos on. Submit a card request.
2. Expected: `201`, the card and payment exist, and the user sees success. The email failure is only logged.

### 8.5 Expiry task

1. ⚠️ Set an active card's end to one minute ago. Before `subscriptions:expire` runs, the public card is already paused (reads compute expiry from the date).
2. Run the task. Expected: `status = 'expired'`; nothing else changes.

## Invariants

1. Every user has exactly one personal workspace (see `02.invitations.md` 5.12 for the onboarding exception).
2. Every personal card belongs to a personal workspace whose only member is the card's `user_id`.
3. Every card has at most one `card_subscription` row.
4. A card has no more than one `submitted` payment at a time.
5. A removed card (`removed_at` set) has no `submitted` payment, appears in no card list or public route, and keeps its `user_id` and contacts.
6. A card whose last paid period has ended is never live because of a `pending_approval` status.
7. No image column stores a full URL; all are keys.
8. Every `approved` payment item's period is reflected in the card's subscription.

## Decisions

| ID  | Gap                                                                                                                           | Decision                                                                                |
| --- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| D2  | A renewal receipt set `pending_approval`, which brought an expired card back online before review; resubmitting kept it live. | **Fixed.** Liveness follows the paid period; only one payment waits per card (5.7–5.8). |
| D3  | Deleting a card cascaded to every contact it collected.                                                                       | **Fixed.** Cards are soft-removed; contacts stay (4.1–4.2a).                            |
| D6  | A newly requested card is public before approval.                                                                             | **Kept.** Live until approved or declined (2.9).                                        |
| D9  | Two overlapping slug changes could hit the unique index as a `500`.                                                           | **Fixed.** Mapped to the same `409` (8.2).                                              |
| D10 | Card views and clicks had no rate limit; a script without cookies could inflate analytics.                                    | **Fixed.** 60 a minute per IP (6.6).                                                    |

Still a product note: changing a slug (3.6) breaks printed QR codes and NFC tags with the old URL; there is no redirect.

## Not covered by e2e

Check by hand when these change:

- Rate limits (6.6), per IP over 5 minutes: the 11th form exchange is `429`; the 301st `POST /api/public/cards/<slug>/interactions` (60 a minute) is `429` and stops counting. A normal visitor never comes close.
- Real uploads to S3 (3.4 uses the upload API only).

## Notes for e2e tests

**Independent tests.** Each part builds its own state with fixtures:

| Part | Needs before it starts                                                               |
| ---- | ------------------------------------------------------------------------------------ |
| 1    | a fresh user (**A**), a platform admin (**T**)                                       |
| 2    | **A** with a personal card; active Standard and Premium plans                        |
| 3–4  | **A** and **B**, each with a personal card                                           |
| 5    | **A** with an active standard card; for 5.6–5.7, `current_period_end_at` in the past |
| 6    | **A**'s card; **B** with a card                                                      |
| 7    | as 3                                                                                 |
| 8    | as 3; a submitted payment for 8.3; Mailpit chaos for 8.4                             |

- **Naming:** `3.3 rejects script links`, matching the step.
- **Receipts and photos:** e2e doesn't run S3. Use a fixture key under `organizations/<space-id>/…` for `receiptUrl` and `avatarUrl`.
- **Prices:** read the plan prices from `subscription_plan` in the test instead of hard-coding them.
- **Time (⚠️):** set `current_period_end_at` in a fixture; don't wait for the task.
