# Invitations: manual test guide

Every way someone is invited into La Persona, and what must stay true when people accept late, accept twice, use the wrong account, or forward the link. There are five kinds:

| Kind                         | Sent by                    | Link                             | Accepting gives                                     |
| ---------------------------- | -------------------------- | -------------------------------- | --------------------------------------------------- |
| Organizer invite             | Thakhin                    | `/invite/community/accept/<id>`  | `admin` (Organizer) membership + community card     |
| Member / volunteer invite    | a community Organizer      | `/invite/community/accept/<id>`  | `member` or `volunteer` membership + community card |
| Join link                    | a community Organizer      | `/invite/community/join/<token>` | `member` membership + community card                |
| Onboarding ("card is ready") | Thakhin                    | `/invite/card/<id>`              | an existing unclaimed card + a free period          |
| Company card invite          | Thakhin or a company admin | `/invite/community/accept/<id>`  | a company card (see `05.companies.md`)              |

Button and field labels come from the code. If one doesn't match the UI, update this guide.

This guide is the source for `tests/02.invitations.test.ts`. Keep step numbers stable, and write every outcome as an **Expected** line that a test can assert. [Decisions](#decisions) at the end records the gaps found while writing it and how each was settled.

## 0. Setup

**Accounts.** Gmail aliases all land in one inbox but count as separate La Persona users.

| Who     | Email                    | Role in these tests                                   |
| ------- | ------------------------ | ----------------------------------------------------- |
| **T**   | your Thakhin admin       | platform admin                                        |
| **O**   | `you+org@gmail.com`      | Organizer of community **Yangon Devs**                |
| **O2**  | `you+org2@gmail.com`     | second Organizer, invited later                       |
| **M**   | `you+member@gmail.com`   | existing user with a personal card, invited as member |
| **VOL** | `you+vol@gmail.com`      | invited as volunteer                                  |
| **N**   | `you+new@gmail.com`      | never signed in before the invite                     |
| **X**   | `you+outsider@gmail.com` | existing user who is never invited                    |
| **P**   | `you+onboard@gmail.com`  | receives an onboarding card invite                    |

**Before you start:** `bun run db:migrate`, the dev mailer sends real email, `bun run dev`. Sign in once as **M** and **X** and create a personal card for each.

**Signing in.** Magic link only (see `01.auth.md`). Don't use Google or LinkedIn for alias accounts: they sign in with the address without `+`, so invites to the alias won't match.

**Time-based states.** Steps marked ⚠️ edit `expires_at` with `bun run db:studio` (a fixture in e2e).

## Part 2.1: Organizer invites (Thakhin)

### 2.1.1 Create a community with an organizer (T)

1. `/thakhin/organizations` → **Create**. Name `Yangon Devs`, Type **Community**, Organizer email **O**.
2. Expected: the community is created with 0 members, and **O** receives "You're invited to organize Yangon Devs on LA PERSONA".
3. Expected: `invitation` row with `role = 'admin'`, `status = 'pending'`, `expires_at` about 7 days out.

### 2.1.2 Organizer accepts as a brand-new account (O)

1. **O** has never signed in. Open the invite link signed out.
2. Expected: you are asked to sign in. Sign in with **O**'s exact alias and return to the link.
3. Click **Accept Invitation**.
4. Expected:
   - **O** lands in the community card setup (or the community home if the card is complete).
   - **O** is an `admin` member, shown as **Organizer** everywhere (never "admin").
   - **O** holds exactly one community card in Yangon Devs, and still has a personal workspace.

### 2.1.3 Invite a second organizer later (T)

1. Thakhin → Yangon Devs → invite organizer **O2**.
2. Expected: `201`, one email to **O2**. **O2** accepts and becomes a second **Organizer**.

### 2.1.3a Inviting the same organizer twice (T)

1. Before **O2** accepts, invite **O2** as organizer again.
2. Expected: `201`, a second email, and still **one** pending `admin` invite for **O2** (the same id), with `expires_at` moved to 7 days from now. The link accepts.

### 2.1.4 Organizer invite to someone already in the community (T)

1. Invite **O** as organizer again.
2. Expected: `409` "This person is already a member of this community." No email.

### 2.1.5 Organizer invites only exist for communities (T)

1. `POST /api/admin/organizations/<company-or-personal-id>/invitations { email }`.
2. Expected: `409` "Only communities have organizers."

### 2.1.6 Expired organizer invite ⚠️

1. Create an organizer invite for **N**, set its `expires_at` to yesterday, open the link as **N**.
2. Expected: "This invitation has expired." and no **Accept Invitation** button. `PATCH /api/invitations/<id> { status: 'accepted' }` returns `409` "This invitation has expired or was already processed."

### 2.1.7 Nobody else can accept an organizer invite (O)

1. With **N**'s organizer invite pending, **O** (an Organizer of the same community) sends `PATCH /api/invitations/<id> { status: 'accepted' }`.
2. Expected: `403` "Only the invitee can accept this invitation." **N** is not added.

## Part 2.2: Member and volunteer invites (Organizer)

### 2.2.1 Invite a member (O)

1. **Members** → **Invite Member**. Email **M**, Role **Member**, **Send Invitation**.
2. Expected: the "Invitation sent" toast. **M** receives "You're invited to join Yangon Devs on LA PERSONA". The Members list shows **M** as **Pending**.

### 2.2.2 Invite a volunteer (O)

1. Invite **VOL** with Role **Volunteer**.
2. Expected: the subject reads "You're invited to volunteer with Yangon Devs on LA PERSONA", and the pending row shows role **Volunteer**.

### 2.2.3 Existing user accepts (M)

1. **M** opens the link signed in as **M** → **Accept Invitation**.
2. Expected:
   - **M** is a `member`, with one community card seeded from their personal card (name, position, phone, avatar, links).
   - **M**'s personal card and personal workspace are unchanged.
   - The pending row is gone from Members; **M** shows as **Active**.

### 2.2.4 New user accepts (N)

1. **O** invites **N**. **N** opens the link signed out, signs in with a magic link for **N**, comes back, accepts.
2. Expected: **N** gets a personal workspace (from sign-up), a `member` membership, and one community card named from their account (first name falls back to "Member").

### 2.2.5 Volunteer accepts (VOL)

1. Expected: membership role `volunteer`. **VOL** can open the event check-in page (`04.communities.md` Part 4.7) but not Members, Settings or Insights.

### 2.2.6 Wrong account opens the link (X)

1. Signed in as **X**, open **M**'s invite link.
2. Expected: "Signed in with another account". The message names the invited address **masked** (`y*******r@gmail.com`), never in full, and adds "You're signed in as <X's email>".
3. `PATCH /api/invitations/<id> { status: 'accepted' }` as **X** returns `403` "Only the invitee can accept this invitation." and nobody is added.

### 2.2.7 Email case doesn't matter

1. **O** invites `You+Case@Gmail.com`. Sign in as `you+case@gmail.com` and accept.
2. Expected: accepted. The invite is stored lower-case.

### 2.2.8 Re-sending an invite replaces it (O)

1. Invite **VOL2** (`you+vol2@gmail.com`), then invite the same address again.
2. Expected: one pending row for that email, a fresh email, and the expiry window restarts. The link in the second email accepts.

### 2.2.9 Invite someone already in the community (O)

1. Invite **M** again after 2.2.3.
2. Expected: "Could not send invite" — "User is already a member of this organization" (`400`), no email.

### 2.2.10 Organizers can't grant Organizer (O)

1. `POST /api/organizations/yangon-devs/invitations { email, role: 'admin' }`.
2. Expected: `400` with `details` naming `role`. No invitation row.
3. The **Invite Member** role picker offers only **Member** and **Volunteer**.

### 2.2.11 Cancel an invite (O)

1. Pending row for **VOL2** → **Cancel invite**.
2. Expected: the "Invite cancelled" toast, the row disappears, and **VOL2**'s link now shows "This invitation was cancelled." Accepting returns `409`.

### 2.2.12 Expired member invite ⚠️

1. Set a member invite's `expires_at` to yesterday. Expected: "This invitation has expired." and accept returns `409`.
2. **O** re-invites the same email (2.2.8). Expected: the new link accepts.

### 2.2.13 Accept twice (M)

1. After 2.2.3, open the same link again.
2. Expected: **Open community** instead of **Accept Invitation** ("You are already a member of this community."). Clicking it opens the community. No second membership or card.

### 2.2.14 Signed-out preview stays private

1. `GET /api/invitations/<id>` signed out returns `401`.
2. `GET /api/public/invitations/<id>` signed out returns `{ email }` only while the invite is pending and unexpired (used to prefill sign-in). After it's accepted, cancelled or expired it returns `404`.
3. Neither response includes the inviter, role or organization.

## Part 2.3: Only the invitee joins

Nobody is added to a community without accepting their own invite. Organizers can resend or cancel a pending invite, never accept it for someone.

### 2.3.1 Resend a pending invite (O)

1. Invite `you+later@gmail.com`. On its pending row, ⋯ → **Resend invite**.
2. Expected: "Invite sent again" — "A new invitation email went to you+later@gmail.com." A second email arrives, there is still one pending row, and its expiry restarts. Nobody is added.

### 2.3.2 Organizers can't accept for an existing user (O)

1. Invite **X** (existing account). As **O**, `PATCH /api/invitations/<id> { status: 'accepted' }`.
2. Expected: `403` "Only the invitee can accept this invitation." **X** isn't a member, no community card is created, and **X**'s personal details aren't copied anywhere.
3. The pending row has no approve action, only **View invite**, **Resend invite** and **Cancel**.

### 2.3.3 Expired invite, resent (O)

1. ⚠️ Expire **X**'s invite. As **O**, try to accept it: `403` as in 2.3.2.
2. **Resend invite**. Expected: a new email, and the link accepts when **X** opens it.

### 2.3.4 Company invites (company admin)

1. A company admin sends `PATCH { status: 'accepted' }` on a pending company card invite.
2. Expected: `403` "Only the invitee can accept this invitation."

### 2.3.5 Organizer invites have no resend here (O)

1. A pending **Organizer** invite (from Thakhin) shows in Members without **Resend invite**. Only Thakhin resends it (2.1.3a).

## Part 2.4: Join links

### 2.4.1 Copy the link (O)

1. **Members** → **Copy invite link**. Expected: "Link copied", a URL `/invite/community/join/<token>`.
2. Copy it again. Expected: the same URL. Join links never rotate or expire (by design).

### 2.4.2 Preview signed out

1. Open the link in a signed-out window.
2. Expected: community name, logo, cover, member and event counts, founded year, and **Sign in to join**.
3. Fetch the page without JavaScript (`curl`). Expected: the HTML already contains the community name, so chat apps can show a preview.
4. `GET /api/public/join-links/<token>` returns `alreadyMember: null` and no member names or emails.

### 2.4.3 Join (X)

1. **X** signs in and clicks **Join community**.
2. Expected: `201`, **X** is a `member` (never volunteer or admin), holds one community card, and lands on the community home.

### 2.4.4 Join again (X)

1. Open the link again as **X** and join.
2. Expected: `200` (not `201`), no second membership or card, and **X** lands on the community home.

### 2.4.5 Bad tokens

1. `/invite/community/join/not-a-token` → "Invite unavailable"; the API returns `404`.
2. A token from a company or personal workspace can't exist; there is no join link for them. `GET /api/organizations/<company>/join-link` returns `404`.

### 2.4.6 Who can see the link

1. As **M** (member) and **VOL** (volunteer): `GET /api/organizations/yangon-devs/join-link` returns `403`.
2. As **X** (not a member): `404`.

### 2.4.7 A removed member rejoins (product decision)

1. **O** removes **X** (Members → remove). **X** opens the join link again and joins.
2. Expected: **X** is back in, with a **new** community card (new slug). The old card stays removed: its link is still "Page not found", and the contacts collected on it still show in **X**'s Contacts. Removal is not a ban, because the link is permanent by design ([D12](#decisions)).

## Part 2.5: Onboarding invites ("Your LA PERSONA card is ready")

Thakhin hands an unclaimed card (a card with no `user_id`, for example a printed NFC card) to someone by email, with free months.

### 2.5.1 Create and send (T)

1. `/thakhin/invitations` → create for **P**: an unclaimed card, plan **Standard**, amount `0`, free months `3`, expiration `1440` minutes, send now.
2. Expected:
   - `201`. **P** receives "Your LA PERSONA card is ready".
   - A new personal workspace `<name>-space-…` exists with **no members**, and the card's `organization_id` points at it.
   - The row shows status **Pending**, resend count 1.

### 2.5.2 New user accepts (P)

1. **P** has never signed in. Open the link, sign in as **P**.
2. Expected: sign-up does **not** create a separate personal workspace for **P**, because an invite is waiting.
3. Click **Accept Invitation**. Expected: "Invitation accepted — Your workspace is now ready."
4. Expected:
   - **P** is `admin` of the invite's workspace, which is now their personal workspace.
   - The card's `user_id` is **P**. Its subscription is `active`, `current_period_end_at` = now + 3 months.
   - One approved 0 MMK system payment, receipt `system:onboarding-invitation:<id>`, paid by **P**.

### 2.5.3 Existing user accepts (M)

1. Create an invite for **M**, who already has a personal workspace. **M** accepts.
2. Expected: the card moves into **M**'s existing personal workspace, the invite's own workspace is deleted, and **M** still has exactly one personal workspace.

### 2.5.4 Wrong account (X)

1. **X** opens **P**'s link. Expected: "Signed in with another account" with the masked address. Accept returns `403`.

### 2.5.5 Accept twice (P)

1. Open the link again after 2.5.2. Expected: "This card is already claimed." and **View cards**. `PATCH` returns `409` "Invitation has already been processed". Still one payment.

### 2.5.6 Expired ⚠️

1. Set `expires_at` to yesterday. Expected: "This invitation has expired."; accept returns `409` "Invitation has expired".
2. **T** resends (`POST /api/admin/onboarding-invitations/<id>/deliveries`). Expected: a new email, `expires_at` restarts from now, resend count +1, and the same link accepts.

### 2.5.7 Cancel (T)

1. Cancel a pending invite. Expected: status **Cancelled**, the card returns to the placeholder organization (unclaimed), and the invite's workspace is deleted. **P**'s link shows "This invitation was cancelled."
2. Cancel an accepted invite. Expected: `409` "Only pending invitations can be cancelled."

### 2.5.8 One open invite per card (T)

1. Create a second invite for the same card while the first is pending. Expected: `409` "Card already has an active onboarding invitation".
2. Create an invite for a card that already has a holder. Expected: `409` "Selected card is already linked to a user".
3. Inactive or unknown plan code. Expected: `409` "Selected subscription plan is invalid".

### 2.5.9 Validation (T)

| Try                                 | Expected |
| ----------------------------------- | -------- |
| `freeMonths` 121, or negative       | `400`    |
| `expirationMinutes` 0, or > 90 days | `400`    |
| `organizationName` 1 character      | `400`    |
| `amountMinor` negative or a decimal | `400`    |

### 2.5.10 Zero free months

1. Create an invite with `freeMonths: 0`.
2. Expected: `400` naming `freeMonths` (minimum 1), because a 0-month invite would hand over a card that is already paused. The Thakhin form's **Free Months** field won't go below 1.

### 2.5.12 Cancelled or expired invite for a new user

Sign-up doesn't create a personal workspace while an onboarding invite is waiting (2.5.2), so a new user whose invite goes away has none. Both cases show a support message instead of a broken page.

1. Create an invite for **N2** (`you+n2@gmail.com`, never signed in). **N2** signs in, then **T** cancels the invite. **N2** opens `/platform`.
2. Expected: "Workspace unavailable — No organization is linked to your account yet. If you were invited to join a workspace, try the invitation link again or contact La Persona for help."
3. ⚠️ Instead of cancelling, expire the invite. **N2** opens the invite link.
4. Expected: "This invitation has expired." with the "Contact La Persona" support link and no **View cards** button (which would loop back to `/platform`).
5. **T** resends (2.5.6). Expected: **N2** accepts and gets their workspace.

## Part 2.7: Access checks (API)

Run each as the named person. Nothing may change on a refused call.

### 2.7.1 Signed out

| Call                                              | Expected |
| ------------------------------------------------- | -------- |
| `GET /api/invitations/<id>`                       | `401`    |
| `PATCH /api/invitations/<id>`                     | `401`    |
| `POST /api/join-links/<token>/members`            | `401`    |
| `GET /api/onboarding-invitations/<id>`            | `401`    |
| `POST /api/organizations/yangon-devs/invitations` | `401`    |
| `POST /api/admin/organizations/<id>/invitations`  | `404`    |

### 2.7.2 Member (M) and volunteer (VOL) of Yangon Devs

1. `POST /api/organizations/yangon-devs/invitations` → `403`.
2. `PATCH /api/invitations/<someone-else's-pending-id> { status: 'canceled' }` → `403`.
3. `PATCH /api/members/<their own member id> { role: 'volunteer' }` → `403`.

### 2.7.3 Organizer of another community

1. **T** creates a second community, **Beta Community**, without **O**. As **O**: `POST /api/organizations/beta-community/invitations` → `404`; cancel a Beta invite → `404`.

### 2.7.4 Organizer can't escalate

1. `PATCH /api/members/<member-id> { role: 'admin' }` → `400` (only `member` / `volunteer` are valid).
2. `PATCH /api/members/<O2's member id> { role: 'member' }` → `403` "The organizer role cannot be changed here."
3. `POST /api/auth/organization/invite-member` (and every other `/api/auth/organization/**` route) → `404`, so better-auth can't be used to bypass the checks above.

### 2.7.5 Personal and company workspaces have no email invites

1. As a personal workspace owner: `POST /api/organizations/<personal-slug>/invitations` → `403` "This is only available for community organizations.", and no email.
2. As a company admin on their company: the same `403` (company invites go through cards only).

### 2.7.6 Onboarding admin routes

1. As **M**: every `/api/admin/onboarding-invitations/**` call → `404`.

## Part 2.8: Reliability (API)

"At once" means overlapping requests (`Promise.all`). No case may return `500`, and the [invariants](#invariants) must hold after each.

### 2.8.1 Accept a community invite in two tabs at once

1. As **M**, send two `PATCH { status: 'accepted' }` at once.
2. Expected: at least one `200`; the other `200` or `409` "This invitation was just accepted. Reload the page." One membership, one community card.

### 2.8.2 Join link double-click

1. As **X**, send `POST /api/join-links/<token>/members` twice at once.
2. Expected: each returns `201` or `200` (whichever finished second may see the membership), never `500`. One membership, one card.

### 2.8.3 Join link and email invite at once

1. **X** has a pending email invite. Accept it and join via the link at once.
2. Expected: one membership, one card. Role is `member` either way.

### 2.8.4 Cancel while the invitee accepts

1. **O** cancels **VOL2**'s invite while **VOL2** accepts.
2. Expected: either the accept wins (VOL2 is a member, cancel returns `409` "already been processed") or the cancel wins (accept returns `409`, no member). Never both.

### 2.8.5 Onboarding accept twice at once

1. As **P**, send two `PATCH /api/onboarding-invitations/<id> { status: 'accepted' }` at once.
2. Expected: one `200`, one `409` "Invitation has already been processed". Exactly one system payment, one payment item, one membership.
3. Check `subscription_payment` where `receipt_url = 'system:onboarding-invitation:<id>'`: there must be **one** row.

### 2.8.6 Create two onboarding invites for one card at once

1. As **T**, send the same create request twice at once.
2. Expected: one `201`, one `409` "Card already has an active onboarding invitation". One pending invite and one new workspace for the card.

### 2.8.6a Cancel while the invitee accepts (onboarding)

1. **T** cancels **P**'s invite while **P** accepts.
2. Expected: one wins. Either **P** holds the card and the cancel returns `409` "Only pending invitations can be cancelled.", or the invite is cancelled and the accept returns `409`. Never a claimed card in a deleted workspace.

### 2.8.7 Email is down

Turn on Mailpit chaos (see `05.companies.md` Notes); turn it off in `finally`.

1. Organizer invite (2.1.1). Expected: `201` and the invite exists; the email failure is logged, not returned. After email is back, inviting again (2.1.3a) delivers one email and the same link accepts.
2. Member invite (2.2.1). Expected: `201` and the pending row exists, but no email arrives (better-auth logs the failure and doesn't report it). After email is back, **Resend invite** delivers one email and the link accepts.
3. Onboarding create with send now (2.5.1). Expected: `502` with the same message. The invite exists as **Pending** with resend count 0, so a retry of the create returns `409` "Card already has an active onboarding invitation"; after email is back, **T** resends it (2.5.6) and it accepts.

## Invariants

After each test, for the community or card the test touched:

1. A person has at most one `member` row per organization.
2. Every community member holds exactly one card in that community, and every community card's holder is a member.
3. A pending invitation's email is not already a member of that organization.
4. Every community with any accepted Organizer invite still has at least one `admin`.
5. An accepted onboarding invitation has exactly one system payment and its card has a `user_id`. A cancelled one's card has none.
6. Every user has exactly one personal workspace, except a user whose onboarding invite is pending, or was cancelled or expired before they accepted (2.5.12).
7. A community has at most one pending invitation per email and role.

## Decisions

Gaps found while writing this guide, and how each was settled.

| ID  | Gap                                                                                                                                                                                          | Decision                                                                                            |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| D1  | An Organizer could add any existing user to their community by inviting and then "approving", with no consent, even after expiry, copying the user's personal details onto a community card. | **Fixed.** Only the invitee accepts (`403` otherwise). Organizers use **Resend invite** (Part 2.3). |
| D4  | A new user with a pending onboarding invite gets no personal workspace; if the invite is cancelled or expires they have none.                                                                | **Kept.** Both cases show a "contact La Persona" message (2.5.12).                                  |
| D5  | Onboarding accept, create and cancel could overlap and both pass the `pending` check.                                                                                                        | **Fixed.** Rows are locked (`FOR UPDATE`) inside the transaction (2.8.5–2.8.6a).                    |
| D10 | `freeMonths: 0` produced a card paused at acceptance.                                                                                                                                        | **Fixed.** Minimum 1 (2.5.10).                                                                      |
| D12 | Join links never rotate, so a removed member can rejoin.                                                                                                                                     | **Kept by design.** Removal is not a ban (2.4.7).                                                   |
| D14 | Thakhin could create several pending Organizer invites for one email.                                                                                                                        | **Fixed.** A repeat refreshes the pending invite (2.1.3a).                                          |
| D15 | Joining by link when already a member returned `201`.                                                                                                                                        | **Fixed.** Returns `200` (2.4.4).                                                                   |

## Not covered by e2e

Check by hand when invitations change:

- Month-end free periods: a 1-month invite accepted on 31 January ends on 3 March (JavaScript `setMonth` rolls over). Needs a fake server clock.
- Google and LinkedIn sign-in with an invited address.

## Notes for e2e tests

**Independent tests.** Each part builds its own state with fixtures (API calls or SQL), so tests don't depend on order:

| Part | Needs before it starts                                                                        |
| ---- | --------------------------------------------------------------------------------------------- |
| 1    | a platform admin (**T**)                                                                      |
| 2–3  | a community with an accepted Organizer (**O**); **M** and **X** signed up with personal cards |
| 4    | as 2, plus the join-link token                                                                |
| 5    | an unclaimed card and an active Standard plan                                                 |
| 6    | a company with a pending card invite for **M**, plus 2                                        |
| 7    | as 2, plus a second community and a company                                                   |
| 8    | as 2 and 5; Mailpit chaos for 2.8.7                                                           |

- **Naming:** `2.2.6 wrong account sees a masked address`, so a failure points back here.
- **Accounts:** a fresh address per run and person (`inv-<run>-org@test.local`).
- **Links:** read invite links from Mailpit. The id is the last path segment.
- **Expiry (⚠️):** set `invitation.expires_at` / `onboarding_invitation.expires_at` in a fixture.
- **Thakhin:** sign up a fresh user and set `user.role = 'admin'`, as in `01.auth.test.ts`.
