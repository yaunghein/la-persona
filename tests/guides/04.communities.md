# Communities: manual test guide

A community from Thakhin setup to a finished event: members and roles, community cards, settings, events, registration, check-in, broadcasts, contacts and insights. Invitations and join links are in `02.invitations.md`; this guide assumes people are already in.

Button and field labels come from the code. If one doesn't match the UI, update this guide.

This guide is the source for `tests/04.communities.test.ts`. Keep step numbers stable, and write every outcome as an **Expected** line that a test can assert. [Decisions](#decisions) at the end records the gaps found while writing it and how each was settled.

## 0. Setup

| Who     | Email                    | Role in **Yangon Devs**              |
| ------- | ------------------------ | ------------------------------------ |
| **T**   | your Thakhin admin       | platform admin                       |
| **O**   | `you+org@gmail.com`      | Organizer (`admin`)                  |
| **O2**  | `you+org2@gmail.com`     | second Organizer                     |
| **M**   | `you+member@gmail.com`   | member                               |
| **VOL** | `you+vol@gmail.com`      | volunteer                            |
| **X**   | `you+outsider@gmail.com` | not a member                         |
| **O3**  | `you+beta@gmail.com`     | Organizer of **Beta Community** only |

Build this with `02.invitations.md` Parts 1–2 (or fixtures). Every member already holds a community card.

**Time-based states (⚠️)** set event `starts_at` / `ends_at` in `db:studio` or a fixture so an event is upcoming, live or past.

## Part 4.1: Thakhin setup (T)

### 4.1.1 Branding

1. Row menu → **Edit**: description, guidelines, why join, logo, cover, Spline URL. Save.
2. Expected: the community About page shows them. Spline must be `https://prod.spline.design/…`; `http://foo` → error, nothing saved.

### 4.1.2 Rich text is sanitized

1. Description `<p>Hi</p><script>alert(1)</script><img src=x onerror=alert(1)><a href="javascript:alert(1)">x</a>`.
2. Expected: stored and shown as `<p>Hi</p>` plus a harmless image/link; no script runs on About, the public community page or the invite preview.

### 4.1.3 Brand assets

1. **Upload assets**: wallpaper, card back, three email images.
2. Expected: keys `uploads/{kind}-yangon-devs.{ext}`. Uploading the same kind again without deleting first → refused. Email images accept only JPG or PNG.

### 4.1.4 Apply to member cards

1. Change the Spline URL with **apply to member cards** ticked.
2. Expected: "Updated N cards", and every member's community card uses the new scene. Without the tick, only new cards get it.

### 4.1.5 Delete rules

1. Delete a community that has cards. Expected: `409` "Remove this organization's cards before deleting it."
2. Delete one with payments. Expected: `409`.
3. Organizers can't delete it: `DELETE /api/admin/organizations/<id>` as **O** → `404`.

### 4.1.6 Background theme

1. Set **Background theme** to **Light** without **apply to member cards**.
2. Expected: existing member cards stay dark. A member who joins afterwards gets a light card.
3. Save again with **apply to member cards** ticked. Expected: every member card is light.

## Part 4.2: Roles and members (O)

### 4.2.1 Members list

1. **Members**. Expected: every member with name, title, company, connections, events attended, role shown with `formatCommunityRole` (**Organizer**, **Member**, **Volunteer**), and pending invites.
2. **Export members**. Expected: a CSV with Name, Email, Phone, Job title, Company, Role, Status, Joined (Yangon time), LinkedIn. Formula-like cells start with `'`.

### 4.2.2 Change roles

1. **M** ⋯ → **Make volunteer**. Expected: "Role updated" — "<name> is now a volunteer." **M** can open check-in.
2. Back with **Make member**.
3. Organizer rows have no role options. `PATCH /api/members/<O2-id> { role: 'member' }` → `403` "The organizer role cannot be changed here."
4. `PATCH /api/members/<m-id> { role: 'admin' }` → `400`.

### 4.2.3 Remove a member

1. **X** has exchanged contacts with **M**'s community card. **O** removes **M**. The dialog says the card's link is retired, registrations here are deleted, and the contacts collected on the card stay with both sides.
2. Expected: `204`, toast "Member removed" — "Their community card link and event registrations here were removed. Contacts collected on the card were kept."
3. Expected: **M** loses the membership and every registration in this community. Their community card is soft-removed (`removed_at` set, `user_id` kept): `/c/<slug>` → "Page not found", and it's gone from Members and **M**'s Cards. **M**'s personal card is untouched, and any session with Yangon Devs active switches away.
4. Expected: **O**'s Yangon Devs Contacts still lists **X** under **M**'s old card.
5. Expected: **M**'s own Contacts still lists **X**, and **M** can label or delete it (`PATCH`/`DELETE /api/contacts/<id>` → `200`/`204`) even though **M** is no longer a member. Re-tagging it with a Yangon Devs event returns `400` "Choose an event you registered for.", because the registrations are gone.
6. **M** rejoins by link (`02.invitations.md` 2.4.7). Expected: a **new** community card; the old one stays removed.

### 4.2.4 Organizer protections

1. **O** removes **O2**. Expected: allowed (two Organizers → one).
2. **O** tries to remove themselves as the last Organizer. Expected: `409` "The last organizer cannot be removed from this community."
3. A volunteer or member calls `DELETE /api/members/<o-id>` → `403`.

### 4.2.5 Quit Community

1. As **M**, About → **Quit Community**. The dialog: "Leave Yangon Devs?" — the card's link stops working, you leave its events, your contacts stay. Click **Leave**.
2. Expected: `DELETE /api/me/organizations/yangon-devs` → `204`, toast "You left Yangon Devs", and **M** lands on `/platform` (their personal workspace).
3. Expected: the same cleanup as 4.2.3: membership, registrations and the card's link gone; contacts kept for **M** and the Organizers.
4. **VOL** quits the same way. Expected: `204`.
5. The last Organizer tries to quit. Expected: "Could not leave" — "The last organizer cannot be removed from this community." (`409`), nothing changes. With two Organizers, one can quit.
6. A company member calls `DELETE /api/me/organizations/<company-slug>`. Expected: `403` "This is only available for community organizations." (company admins offboard members).
7. A non-member calls it. Expected: `404`.

### 4.2.6 Organizers can read, not edit, a member's card

1. As **O**, `PATCH /api/cards/<m-community-slug>` with new links and a new slug.
2. Expected: `403` "Only the card holder can edit this card." Nothing changes.
3. `GET /api/cards/<m-community-slug>` as **O** → `200` (Organizers can still read it). **View Persona Card** in the member profile opens the public card, not an editor.
4. **O** edits their **own** community card → `200`. A company admin editing a company card is unchanged (`05.companies.md` 5.4.4).

## Part 4.3: Community cards

### 4.3.1 Seeded from the personal card

1. A user with a personal card joins. Expected: the community card copies first/last name, position, company, phone, email, website, avatar and links, and uses the community's Spline, wallpaper and card back.
2. A user with no personal card. Expected: name from the account (`Member` if empty), position `Member`.

### 4.3.2 Setup flow

1. A new member with an incomplete card lands on `/platform/yangon-devs/cards/<slug>/community-setup?step=create-card`. Completing it lands on the community home.

### 4.3.3 Never pauses

1. ⚠️ Give a community card an expired subscription row. Expected: still live; exchange works. No renewal UI, and `GET /api/cards/<slug>/payment-quote` → `403`.

### 4.3.4 Can't be deleted directly

1. `DELETE /api/cards/<community-slug>` as its holder → `403`, and the card stays. (Members lack `card:delete`; an Organizer deleting their own card gets "Community cards are removed when you leave the community.")

### 4.3.5 One card per member

1. Thakhin "create member card" for someone who has one → `409` "This member already has a community card."
2. For a non-member → `404`.

## Part 4.6: Registration

### 4.6.1 Open event, member registers (M)

1. On `/events/<id>`, **Register**. Expected: `201`, status `registered`, **M** gets a confirmation email and the Organizers a notification.
2. Register again. Expected: `200` with the same registration; no second row or email.

### 4.6.2 Non-member registers from the public page (X)

1. **X** opens `/events/<id>`, signs in, registers.
2. Expected: **X** joins Yangon Devs as `member` (with a community card) and is registered. The join returns `201`; a second call returns `alreadyMember: true`.

### 4.6.3 Manual approval

1. Event with approval **manual** and capacity 1. **M** and **VOL** register. Expected: both `pending`; no seat taken.
2. **O** approves (`PATCH /api/registrations/<id>`). Expected: `registered`, **M** gets the confirmation.
3. Approve when the event is full → `409` "This event is at capacity." Approve after the event ended → `409` "This event has ended."

### 4.6.4 Closed and invite-only

1. Registration **closed**: register → `403` "Registration is closed for this event". **X** can't join the community through it either.
2. **invite only**: `403` "This event is invite only".

### 4.6.5 Capacity

1. Capacity 2, two registered. A third registers → `409` "This event is at capacity". Pending registrations don't count.
2. One cancels. Expected: the third can now register.

### 4.6.6 Cancel own registration

1. **M** unregisters. Expected: `204`; doing it again is also `204`.
2. After check-in: `409` "Checked-in attendees cannot unregister."

### 4.6.7 Past events

1. ⚠️ Event ended. Register → `403` "This event has ended". Join from the event page → refused too.

### 4.6.8 Attendee labels carry over

1. **O** labels **M** "VIP" on event 1, with "carries over" on. **M** registers for event 2. Expected: "VIP" is already on the new registration. A label without carry-over isn't.

## Part 4.7: Check-in (VOL and O)

### 4.7.1 Before and after the event day ⚠️

1. Event tomorrow: scanning returns `409` "Check-in opens on the event day."
2. Event ended: `409` "This event has ended."

### 4.7.2 Scan a registered member (VOL)

1. **Check in with scanner** → scan **M**'s community card QR.
2. Expected: the attendee card (name, title, company, phone, email), then "Checked in". **M** gets the check-in email. Scanning again shows already checked in and sends nothing.

### 4.7.3 Scan someone not registered

1. Scan the card of a member who isn't registered. Expected: `GET /api/events/<id>/tickets/<slug>` → `{ status: 'not_found', slug }`, and the scanner offers **Register as walk-in**.
2. Scan a **personal** card or a Beta community card. Expected: not found. Check-in accepts only this community's cards.
3. Scan a pending (manual approval) registration. Expected: not found.

### 4.7.4 Walk-in without email (VOL)

1. **No email check-in**: Full Name, Phone Number, Professional Title, **Save and check in**.
2. Expected: a checked-in registration with **Walk-in** badge and "No Email" in exports. Capacity and registration mode don't apply; only the check-in window does.

### 4.7.5 Self walk-in (X)

1. Registration **open**: during the event, **X** opens `/events/<id>/walk-in`, signs in, registers.
2. Expected: **X** joins the community and is registered as `walk_in`. Full capacity blocks: `409` "This event is at capacity".
3. Registration **closed** or **invite only**: a non-member **X** tries the same.
4. Expected: `403` "Registration is closed for this event" / "This event is invite only" on both the join (`POST …/walk-in-memberships`) and the registration (`POST …/walk-in-registrations`). **X** doesn't join the community.
5. A member who registered online before registration closed opens the walk-in page. Expected: they get their existing registration (`200`), not a `403`.
6. Staff can still add guests without email (4.7.4) at closed or invite-only events.
7. Outside the window: `404`.

### 4.7.6 Attendee list and export

1. **VOL**: attendee list loads; **Export registered attendees** → `403`.
2. **O**: both exports download; check-ins export only checked-in rows. Times are in the event's time zone.

### 4.7.7 Members can't check in

1. **M**: `POST /api/events/<id>/check-ins` → `403`; `GET …/tickets/<slug>` → `403`; `GET …/registrations` → `403`.

## Part 4.8: Broadcasts (O)

1. **Reminder** before the event. Expected: `202`; every registered attendee with an email gets one reminder; walk-ins without email are skipped.
2. **Reminder** after the event → `409` "This event has ended."
3. **After event** before it starts → `409` "This event has not started yet."
4. Volunteer or member: `POST /api/events/<id>/broadcasts` → `403`.
5. Send the reminder again. Expected: `409` "This email was already sent for this event." and no second email. The modal shows "Sent <date>" — "Each of these emails goes out once per event." with **Send** disabled.
6. Two Organizers send the reminder at the same moment. Expected: one `202`, one `409`; every attendee gets exactly one reminder.
7. Once the event has started, the **after event** email still sends (`202`): each kind has its own once-only flag.
8. An event with no one to email returns `400` "No registered attendees to email" and does **not** use up its send.

## Part 4.10: Isolation (API)

**O3** (Organizer of Beta only) on Yangon Devs — every call `404`, nothing changes:

- `GET /api/organizations/yangon-devs/members`, `/contacts`, `/insights`, `/join-link`, `/events`
- `PATCH /api/organizations/yangon-devs`
- `DELETE /api/members/<m-id>`, `PATCH /api/members/<m-id>`
- `PATCH /api/events/<yangon-event>`, `POST /api/events/<yangon-event>/check-ins`, `/broadcasts`
- `PATCH /api/registrations/<yangon-registration>`
- `PATCH`/`DELETE /api/attendee-labels/<yangon-label>`
- `POST /api/organizations/yangon-devs/uploads`

On community-only routes (`/events`, `/join-link`, `/members`), a company or personal workspace returns `403` "This is only available for community organizations." to its own members and `404` to everyone else.

## Invariants

1. Every community has at least one `admin` (once an Organizer has accepted).
2. Every member holds exactly one live (`removed_at` null) card in the community; every live community card's holder is a member.
3. A removed community card keeps its `user_id` and its contacts; it appears in no member list, card list or public route.
4. Each event's `reminder_email_sent_at` and `after_event_email_sent_at` are set at most once.
5. A person has at most one registration per event (`event_registration_event_user_uidx`).
6. An event never has more `registered` + `checked_in` registrations than its capacity, except staff walk-ins (4.7.4), which bypass capacity by design.
7. A `checked_in` registration has `checked_in_at` set; others don't.
8. No registration belongs to a user who isn't a member of the event's community (walk-ins without accounts excepted).
9. Every `organizerMemberId` in community settings points at an `admin` of that community.

## Decisions

| ID  | Gap                                                                               | Decision                                                                                         |
| --- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| D3  | Removing a member deleted their community card and every contact collected on it. | **Fixed.** The card is soft-removed; contacts stay with the member and the Organizers (4.2.3).   |
| D6  | Two scanners could both check someone in and both send the email.                 | **Fixed.** Check-in only updates a not-yet-checked-in row (4.11.3).                              |
| D7  | A double register could hit the unique index as a `500`.                          | **Fixed.** The second returns the existing registration (4.11.2).                                |
| D8  | Members couldn't leave a community.                                               | **Fixed.** **Quit Community** (4.2.5).                                                           |
| D11 | Broadcasts could be resent any number of times.                                   | **Fixed.** Once per kind per event (Part 4.8).                                                   |
| D13 | Self walk-ins ignored closed and invite-only registration.                        | **Fixed.** Refused for non-members; staff walk-ins and existing registrations unchanged (4.7.5). |
| D16 | Organizers could edit members' community cards.                                   | **Fixed.** Read-only for Organizers (4.2.6).                                                     |
| D17 | The first settings reads at once could both insert the row and `500`.             | **Fixed.** The insert skips an existing row and re-reads it (4.11.8).                            |

Also in `02.invitations.md`: D1 (only the invitee accepts) and D12 (removed members can rejoin by link, by design).

## Not covered by e2e

Check by hand when these change:

- Removing a member at the exact moment they register can leave one registration behind (the register passed its membership check just before the removal). Narrow and harmless; invariant 8 would show it.
- Camera scanning (e2e calls the check-in API with the card slug).
- Real uploads to S3 (4.1.3, 4.4.1).

## Notes for e2e tests

**Independent tests.** Each part builds its own state with fixtures:

| Part | Needs before it starts                                                                                    |
| ---- | --------------------------------------------------------------------------------------------------------- |
| 1    | a platform admin and a community                                                                          |
| 2–4  | Yangon Devs with **O**, **O2**, **M**, **VOL**, each holding a community card; **X** with a personal card |
| 5–6  | as 2, plus an upcoming event (capacity and modes set per step)                                            |
| 7    | as 2, plus a live event (started 1 hour ago, ends in 1 hour) with **M** registered                        |
| 8    | as 7, plus a past event                                                                                   |
| 9    | as 2; **X** exchanges with **M**                                                                          |
| 10   | as 2, plus Beta Community with **O3**                                                                     |
| 11   | as 5 and 7; Mailpit chaos for 4.11.7                                                                      |

- **Naming:** `4.7.2 volunteer checks in a registered member`.
- **Event phases:** create events with `starts_at` / `ends_at` relative to now in a fixture (live = started 1 hour ago, ends in 1 hour). Check-in phase uses the event's time zone, so set one explicitly.
- **Scanning:** call `POST /api/events/<id>/check-ins { cardSlug }` instead of driving the camera.
- **Overlap cases:** `Promise.all` with one request context per person; no sleeps.
- **Email:** assert recipients and subjects in Mailpit; for 4.11.3 assert exactly one check-in email.
